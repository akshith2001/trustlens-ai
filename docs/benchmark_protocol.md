# Benchmark protocol

## Purpose

The TrustLens benchmark separates three kinds of evidence that must not be
conflated:

1. development-only comparison on the historical credit case study;
2. one previously locked final evaluation, which benchmark commands never run;
3. controlled synthetic robustness studies that test code and methodology but
   do not establish external validity.

## Predeclared ranking

Historical development candidates are ranked by:

1. lowest mean weighted error cost across shared stratified folds;
2. highest mean balanced accuracy;
3. lexicographic model name as a deterministic final tie-breaker.

The experimental cost is five units for a false negative and one unit for a
false positive. This is a research assumption, not a stakeholder-derived value.

## Controlled datasets

The suite contains two deterministic synthetic cases generated with fixed
seeds:

- a balanced, mostly linear 12-feature classification problem;
- an imbalanced, nonlinear 16-feature problem with three clusters per class.

They test expected behaviour under known construction choices. They are not
substitutes for contemporary, multi-institutional or prospective data.

## Statistical analysis

All candidates use shared stratified folds. The suite reports:

- balanced accuracy;
- weighted error cost per record;
- deterministic 95% percentile bootstrap intervals;
- a paired bootstrap interval for the random-forest minus logistic-regression
  difference in per-record cost.

A paired interval that excludes zero is evidence of a difference on the
controlled dataset under this protocol. It is not proof that either model will
be better on a new domain.

## Controlled shift

After a stratified train/test split, the first three test features are shifted
by 1.5 training standard deviations while labels remain fixed. The reported
balanced-accuracy delta is a stress test of covariate sensitivity. It is not a
real temporal validation because the source has no genuine timestamps.

## Reproducibility requirements

- Dataset and generator identities must be versioned.
- Random seeds, fold counts, cost definitions and bootstrap counts must be
  recorded in machine-readable results.
- All candidate models must use identical folds.
- Locked final-test files must not be overwritten or regenerated by benchmark
  commands.
- Negative and contradictory findings must remain in reports.

## Interpretation boundary

The benchmark measures reproducibility and controlled robustness. Operational
claims require contemporary external data, temporal validation, stakeholder
input, subgroup sample-size planning, prospective evaluation and evidence about
human-review performance.
